## 1. 升级背景与必要性

**结论先行：应尽快升级（必要性 High），但非强制硬分叉、有容忍窗口。**

官方表述优先：v1.9.1 release 的 Update Priority 表把 **RPC Nodes = High**（Validators 亦 High），并明确写 "Operators running v1.9.0 should upgrade to v1.9.1"。这正中 DeBank 的部署角色（只读 RPC/follow 副本），是必要性高的直接信号——与同期 oas v1.9.1 的 optional/not-mandatory 相反。

但 v1.9.1 **不是强制硬分叉**：其携带的协议变更（TIP-1067 / TIP-1060 / TIP-1075，详见下）全部 gated 在 **T7/T8 未来 hardfork** 后，当前 production 未激活。不升不会在某个 activation timestamp 掉出共识，因此是"应尽快升"而非"激活前必升"。

### v1.9.1 主要更新内容（过只读 follow 副本筛后）

落在 DeBank 同步/采集路径上的真实收益：

1. **follow-mode resubscription 修复（核心收益）**——certified follow 设为默认 + upstream event stream 出错/终止后重新订阅（`crates/consensus/src/follow/upstream/actor.rs` +175、`bin/tempo/src/follow.rs`）。DeBank 的 tempo 副本正是 follow 模式跟随 upstream，无此修复时遇流中断可能**静默停止同步、供旧数据**。直接落在 DeBank 同步路径上。
2. **`tempo_simulateV1` metadata block 选择一致性**——API 正确性修复（若使用 simulate）。
3. **Reth / Alloy 依赖 bump + MSRV 1.96**——维护性。推迟会加大下次 merge 难度（reth rev `72fafb5→7e3e0c0`、alloy `2.0.5→2.1.0`、revm `40→41`）。

不构成 DeBank 收益的 inert 项（validator/builder 侧或 future-fork 死代码，撑大了 v1.9.1 的 delta 但对只读副本无影响）：builder cache sharing 开关、payload-builder latency、executor actor deferring drops、多数 tx-pool 性能改动；以及三项 **T7/T8-gated 未激活**协议变更——TIP-1067 Dynamic Base Fee、TIP-1060 SSTORE Storage Credits、TIP-1075 Disable TIP-20 Rewards。

### DeBank 侧 build blocker（升级注意点，非收益）

v1.9.1 MSRV = **1.96**，而 `Dockerfile.debank` 原钉 `rust:1.93`，不 bump 则 CI build 失败。本次已修（见 §2）。

> 必要性与"是否触碰敏感路径"正交：v1.9.1 触碰了同步正确性（follow-mode）、API 正确性（rpc/simulate）、数据正确性（revm/evm/handler，需确认是否影响已激活 fork），**involved=true**，需实测 debank-rpc 输出一致性（见 §4）；但必要性由官方 RPC High 表述决定，与 delta 大小、命中文件数无关。

### 双向影响分析

**反向影响（debank patch → 新代码正确性）：无 severe**

- **`node.rs` EthApi 类型参数变化**（`TempoEthApi<N>` → `TempoEthApi<NodeAdapter<N>>`，upstream 改动）影响 debank hook 的注册站（`node.rs:297/317-326` 注册 `PreApi`/`DebankEthExt`/`DebankTraceBlock`）。三个 debank RPC 构造器均为泛型 `<Eth: EthApiTypes + …>`，具体类型变化被泛型**透明吸收**，无源码改动；`node.rs` 干净合并（`M`），hook 完整、行为无变化。`introduced_by_merge=true` 但 `inert_for_replica=true`（行为对只读副本透明，编译正确性交 build gate 响亮兜底）。
- **`Cargo.toml/Cargo.lock` 冲突解决**：潜在高风险（整解丢 patch）已被正确解决消除，as-resolved 跨 4 文件一致，无残留缺陷。`inert`。
- **debank-rpc 回放路径 `.unwrap()` panic 风险**：`introduced_by_merge=**false**`（pre-existing，upstream 从不触碰 `crates/debank-rpc/`，本 merge 未改一行）→ **不计入本次 severity**。但 v1.9.1 新 tx/费用类型可能在未改的回放循环里新触发，记 hardening TODO（见 §5）。

**正向影响（upstream → debank 采集）：下游需跟进项（非 merge blocker）**

三项协议变更均 **T7/T8-gated、当前 production 未激活**，采集复用链本身 EVM、结构性忠实捕获，无本次 merge introduced 的采集正确性缺陷（`severe=false`）。激活后下游需知悉（见 §5）：

- **TIP-1067 Dynamic Base Fee**：静态 per-hardfork base fee → EIP-1559 式 per-block 控制器。采集侧 `DebankBlock.base_fee_per_gas` 直接读 header 实际值（`trace_block.rs:66/94`、`pre.rs:125`），自动捕获动态值，cap `1.2e10` 不溢出；不引用被删的 `base_fee()` 方法、不 hardcode 常量 → 无破坏。
- **TIP-1060 SSTORE Storage Credits**：新 precompile，state_diff 经 `DatabaseCommit` 忠实捕获其 storage slots，trace gas_used 反映新 SSTORE 计费 → 结构性捕获。
- **TIP-1075 Disable TIP-20 Rewards**：T7+ `setRewardRecipient`/`distributeReward` 变 no-op。state_diff/trace 忠实捕获 reward 状态转移停止；`erc20_handle.rs` 只处理 native token sentinel selector，与 reward 机制无关，不受影响。

## 3. 部署情况（backup writer 测试形态）

**生产形态**：tempo **尚未迁移通用节点管线**——生产 pod 单 `node` 容器（`jrpcx` 仅 configmap，node 代码零引用），**无 background-tracer sidecar**，node 不向 Kafka/S3/etcd 投递、不选主。DeBank 自定义 RPC（`trace_debankBlock`/`eth_multiCall`/`pre_traceMany`）是 **pull 拉取**，非 node push。

**测试部署**：单 `tempo node` 容器，dev box（x86_64 → 必须 amd64 镜像），从生产 seed 快照（60 GiB，约 4 天龄）建卷恢复，`--chain=mainnet`（PRESTO，chainId 4217）+ `--follow=auto`（`wss://rpc.presto.tempo.xyz`）跟随官方 WS 同步。

**is_backup：N/A——本家族（reth-Rust）无此机制**。`rg` 全库 `VMTRACE_JSONCONFIG` 零出现、`is_backup` 仅出现在历史笔记，代码无该 env/概念/live tracer json cfg。隔离靠结构性手段而非关开关：
1. RPC/WS 绑 `127.0.0.1`、不公开、不挂任何生产 RPC 端点组；
2. **无下游投递管线可污染**（自定义 RPC 是 pull 拉取）——因此 `--http.api=all --ws.api=all` 全开运行，本次要验证的 RPC 产出（自定义 RPC parity，§4）真实跑起来、真实可验证；
3. 首启前清 p2p 身份（`<datadir>/discovery-secret`、`<datadir>/known-peers.json`，照生产 bootnode initContainer），让 peerid 重生，避免与生产 writer p2p 身份相撞影响其同步。

无 S3/AWS 凭证需求（node 不访问 S3）。

> 新家族回写：tempo = reth 系 Rust 节点，is_backup 机制 **N/A（被动 RPC follower，无投递管线）**；隔离 = `127.0.0.1` bind + 不挂端点组 + p2p 身份清理；S3 凭证不需要；caveat = 若日后迁入 background-tracer sidecar，须重新评估其 backup 注入。

## 5. 其他问题 / 后续跟进

1. **debank-rpc 回放路径 `.unwrap()` panic 风险（pre-existing，med，hardening TODO）**：`trace_block.rs:73/423/450`、`multi_call.rs:73` 在空/边界结果上可 panic（`trace_block.rs:423` 仅靠软不变量守护）。非本次 merge 引入（upstream 从不触碰 debank-rpc），故不计入本次 severity；被 JSON-RPC server per-request 任务隔离，只失败单个 trace 请求、不崩 sync/consensus。但 v1.9.1 新 tx/费用类型（**TIP-1060 storage credits、AA-2D**）可能在未改的回放循环里**新触发**——建议在 T7/T8 激活前对这几处加显式边界检查。
